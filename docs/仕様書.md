### 2.2 テックスタック

- **Container:** Docker / Docker Compose
- **Application:** Python (FastAPI / Flask) または Node.js
- **Scheduler:** Docker Compose で起動する常駐ワーカー。1分ごとにDBを参照して送信対象を判定
- **Database:** SQLite (軽量・ファイルベース。コンテナボリュームで永続化)
- **Networking:** Cloudflare Tunnel (`cloudflared`) の発行 URL を公開エンドポイントとして利用
- **External API:** LINE Messaging API (Free Plan), Slack Incoming Webhook

### 2.3 データベース設計 (SQLite)

最小構成を想定。送信スケジュールとアラート閾値もDBで管理する。

#### `check_ins` テーブル (安否確認レコード)

| カラム名     | 型       | 説明                                     |
| ------------ | -------- | ---------------------------------------- |
| id           | INTEGER  | PK                                       |
| schedule_id  | INTEGER  | 送信スケジュール ID                      |
| scheduled_at | DATETIME | 送信予定時刻                             |
| sent_at      | DATETIME | 実際に送信した時刻                       |
| replied_at   | DATETIME | 家族がボタンを押した時刻（NULLは未回答） |
| status       | TEXT     | `pending`, `success`, `alert`            |

#### `message_schedules` テーブル (送信スケジュール)

| カラム名     | 型       | 説明                              |
| ------------ | -------- | --------------------------------- |
| id           | INTEGER  | PK                                |
| label        | TEXT     | 設定名（例: 朝, 昼, 夜）          |
| time_of_day  | TEXT     | JST基準の `HH:MM` 形式の送信時刻  |
| days_of_week | TEXT     | 実行曜日。現時点では `daily` 固定 |
| is_active    | BOOLEAN  | 有効フラグ                        |
| updated_at   | DATETIME | 更新日時                          |

備考:

- タイムゾーンは `Asia/Tokyo` 固定。
- `days_of_week` は将来拡張用の予約カラムとし、現時点では全レコード `daily` のみを許容する。

#### `app_settings` テーブル (運用設定)

| カラム名   | 型       | 説明                                   |
| ---------- | -------- | -------------------------------------- |
| key        | TEXT     | PK。`alert_after_hours` などの設定キー |
| value      | TEXT     | 設定値                                 |
| updated_at | DATETIME | 更新日時                               |

### 2.4 主要ロジック・アルゴリズム

#### A. メッセージ送信処理（scheduler コンテナ常駐 / 1分ごと実行）

1. Docker Compose で起動した scheduler コンテナ内の常駐ワーカーが、1分ごとに処理を実行する。
1. ワーカーはタイムゾーンを `Asia/Tokyo` として現在時刻を取得する。
1. `message_schedules` テーブルから `is_active = true` かつ `days_of_week = daily` の設定を取得する。
1. 現在時刻の `HH:MM` と `time_of_day` が一致する設定ごとに、当日分の `check_ins` レコードが未作成であることを確認する。
1. 未作成であれば、 `check_ins` テーブルへ `schedule_id` 付きのレコードを `pending` 状態でインサートする。
1. LINE APIの「Flex Message」を使用して、ボタン付きメッセージを送信する。
1. `sent_at` を更新する。

#### B. レスポンス受信処理（Webhook経由）

1. LINEからのWebhook（Postbackイベント）を受信。
1. 対象の `check_ins` レコードを特定し、 `replied_at` を現在時刻、 `status` を `success` に更新。

#### C. 監視・アラート処理（定期実行 / 例: 5分ごと）

1. `app_settings` テーブルから `alert_after_hours` を取得する。
1. `status` が `pending` かつ `sent_at` から設定時間を超過したレコードを抽出する。
1. 該当があれば `status` を `alert` に更新する。
1. 管理者（自分）のSlackへ「【至急】安否確認の返信がありません」と通知する。

#### D. 設定管理処理（将来 GUI から実行）

1. 送信時刻設定は `message_schedules` テーブルを更新して管理する。
1. アラート閾値などの共通設定は `app_settings` テーブルを更新して管理する。
1. scheduler ワーカーと監視処理は、実行時に最新設定をDBから読み出して反映する。

#### E. スケジューラ実装方式

1. 送信時刻の到達判定は、OS の cron ではなく、Docker コンテナ内で動作する常駐 scheduler ワーカーで実装する。
1. scheduler ワーカーは1分間隔で `message_schedules` を参照するため、GUI から設定を更新した場合でも再起動なしで次回判定から反映できる。
1. API コンテナと scheduler コンテナは分離し、Webhook 応答と定期実行を独立して運用する。

### 2.5 API 仕様（Webhook）

- **Endpoint:** `POST /webhook`
- **Authentication:** LINEの署名検証（X-Line-Signature）を実施。
- **Event Type:** `postback` (ボタン押下時)

### 2.6 運用上の制約

自宅サーバーが停電やフリーズで止まった場合、安否確認メッセージ送信と未返信アラート送信は停止する。

- **現時点の方針:** 外部からの死活監視やヘルスチェックは実装しない。
- **公開 URL:** LINE Webhook の公開先には Cloudflare Tunnel の発行 URL を利用する。
